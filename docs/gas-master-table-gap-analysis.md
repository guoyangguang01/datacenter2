# 燃气总表与当前项目的适配差异分析

> 日期：2026-11-13
>
> 基线：`3899ece refactor: align point directions with gas master table`
> 数据样本：`fuel-csv-utf8.csv`

> 2026-11-15 实施状态：燃气总表系统级导入/导出、系统/客户端分组、统一 PointLink 关系表、
> TCP 批量读写协议和“燃油系统”内置样例已落地。数字型 OPC UA NodeId 仍按约定暂缓。

## 1. 结论

当前项目的方向语义已经与燃气总表对齐：

- `INPUT`：第三方数据进入软件侧，作为分发来源。
- `OUTPUT`：软件侧向一个或多个集成方分发数据。
- 一个 INPUT 值可以路由到多个 OUTPUT。

当前主要缺口不再是 `INPUT/OUTPUT` 含义相反，而是：

> 燃气总表是一张跨多个数据用户的扁平路由表，当前项目仍然按单客户端点表目录保存数据。

要让项目完整承载这份总表，还需要补齐总表导入、目标测点解析、协议参数映射、目标-only 用户处理和运行期交付闭环。

## 2. 数据规模

当前燃油/燃气总表样本共包含：

- 732 条数据行；
- 200 个 `(用户代码, 测点id)` 逻辑点；
- 366 条输入关系；
- 366 条输出关系。

每个逻辑点的输出分发关系数量：

| 每个点的输出关系数 | 点数 |
|---:|---:|
| 1 | 59 |
| 2 | 116 |
| 3 | 25 |

当前项目的路由能力支持一个 INPUT 向多个 OUTPUT 扇出，因此上表中的 1:N 关系本身不是阻塞项。阻塞点在于如何把总表的行安全、稳定地归一化到当前模型。

## 3. 已适配的部分

| 能力 | 当前实现 | 状态 |
|---|---|---|
| INPUT/OUTPUT 语义 | `INPUT` 为数据来源，`OUTPUT` 为分发目标 | 已适配 |
| 一个 INPUT 分发到多个 OUTPUT | `PointRouter.ResolveOutputTargets` 返回全部匹配目标 | 已适配 |
| 跨客户端引用 | 支持 `clientCode:pointId` | 已适配 |
| 同客户端引用 | 支持本地 INPUT/OUTPUT 引用 | 已适配 |
| 当前样本的数据类型 | `bool`、`double` 已可映射到 `Bool`、`Float64` | 已适配 |
| 当前样本的用户协议 | 每个用户代码对应一种协议 | 当前数据可用 |

## 4. 阻塞级不适配

### 4.1 燃气总表不能直接导入

当前 CSV 导入器只接受内部点表格式：

```text
pointId,pointName,dataType,unit,direction,address,sourceInputPointId,deadband,group
```

燃气总表使用中文列，并包含：

- 用户代码；
- 测点类型；
- 数据来源用户代码；
- 数据来源测点；
- 数据去向用户代码；
- 数据去向测点；
- 两组同名的 `参数1/参数2/参数3`。

当前导入器无法直接读取这种格式，因此原始总表不能直接进入系统。

### 4.2 总表一行不是一条测点定义

当前导入器按 CSV 行生成测点行，并在同一客户端内检查重复 `PointId`。

燃气总表同一逻辑点会同时出现：

- 一条或多条输入关系；
- 一条或多条输出关系。

如果未经归一化直接导入，会触发测点 ID 重复。正确流程应为：

```text
按 (用户代码, 测点id) 分组
  → 生成一个 INPUT 源端点
  → 为该点的每条输出关系生成目标 OUTPUT
  → 用 sourceInputPointId 指向同一个 INPUT
```

### 4.3 目标 PointId 通过统一规则构造

总表 pointId 的构造规则为：

```text
客户端代码 + 五位数字 + -d/-b
```

目标 PointId 不再依赖目标测点名猜测，而是保留来源 pointId 的“五位数字 + 后缀”，替换客户端代码：

```text
FZXT10001-b + 目标客户端 XNCZ
→ XNCZ10001-b
```

总表 200 个输入 pointId 全部符合该格式。当前仍需在导入器中统一实现和校验该规则。

### 4.4 OPC UA 参数需要结构化，数字型 NodeId 暂缓

总表输入行和输出目的端的参数均为 OPC UA 参数：

```text
参数1, 参数2, 参数3
```

当前明确支持字符串型 NodeId：

```text
参数1=1, 参数2=S, 参数3=FZXT10001_B
→ ns=1;s=FZXT10001_B
```

数字型 NodeId 暂不处理。当前总表中有 22 个 XNCZ 输入点只填写 `参数1`，例如 `5027`，导入时应标记为不支持并要求人工处理。

当前 `PointDefinition` 仍只有一个 `Address` 字符串，不能无损保存原始三参数和两组参数。需要增加结构化 OPC UA 绑定：

```text
OpcUaParameter1
OpcUaParameter2
OpcUaParameter3
OpcUaNodeId
```

### 4.5 `SWGZ` 是目标-only 用户

总表中有 116 条输出关系指向 `SWGZ`，但 `SWGZ` 没有自己的完整逻辑点分组和地址定义。

业务上允许 `SWGZ` 只作为输出目标存在。当前项目需要：

- 已登记的目标客户端；
- 提前配置客户端连接；
- 根据目标客户端代码和 pointId 规则生成目标 ID；
- 按 TCP 批量发送语义接入，不再要求逐节点地址。

`SWGZ` 不需要构造 INPUT，只保留输出的数据模型是允许的。

### 4.6 跨客户端导入没有事务边界

当前保存点表按单个 `clientCode` 执行。总表覆盖多个数据用户，逐客户端导入会产生部分成功：

- 第一个客户端保存成功；
- 后续客户端解析或保存失败；
- 系统停留在不完整的路由配置状态。

需要增加：

- 全量预检；
- 跨客户端变更计划；
- 全部通过后的统一提交；
- 失败时回滚或保持旧配置不变。

跨客户端导入只处理点表和路由数据。所有客户端必须提前创建并完成连接配置；导入器不创建客户端，也不修改连接参数。

## 5. 运行期不适配

### 5.1 目标离线时数据分发丢失

当前 INPUT 变化后会依次向 OUTPUT 目标发送写命令。目标客户端离线时只记录日志，没有保存最新期望值，也没有在重连后补发。

对多个集成方分发场景，这会造成：

- 在线集成方收到数据；
- 离线集成方永久缺失该次数据；
- 源值保持稳定时，离线方恢复后也无法自动追平。

需要为每条 OUTPUT 路由保存最新期望值，并在目标恢复后补发。

### 5.2 多目标发送是串行链路

当前分发逻辑逐个等待目标发送结果。一个目标发送慢时，会推迟后续目标。

TCP 目标应使用批量发送，不要求逐节点地址。服务端需要按目标客户端聚合 OUTPUT 后发送，并让不同目标之间相互隔离。

需要至少做到：

- 按目标隔离发送；
- 独立超时；
- 独立失败计数；
- 单个慢目标不阻塞其他目标。

### 5.3 缺少路由级交付状态

当前能够看到客户端通讯状态和最新值，但无法直接确认：

- 某条 INPUT 已分发给哪些 OUTPUT；
- 每个 OUTPUT 是否成功接收；
- 最后一次成功/失败时间；
- 失败后是否重试成功。

建议增加路由级状态：

```text
SourceInput
TargetOutput
Enabled
LastDispatchAt
LastAckAt
DeliveryState
FailureCount
LastError
```

## 6. 条件性限制

当前客户端模型是“一个客户端进程对应一个设备协议连接”。本次样本中每个用户代码只对应一种协议，因此当前可用。

如果未来同一用户需要同时使用 TCP 和 OPC UA 等多个连接，或同一用户的不同测点需要不同连接配置，现有客户端模型仍需要扩展。

## 7. 建议实施顺序

### P0

1. 新增燃气总表专用解析器，不复用逐行内部点表导入逻辑。
2. 按 `(用户代码, 测点id)` 归一化一个 INPUT 和多个 OUTPUT。
3. 实现目标 `PointId` 构造和格式校验。
4. 定义字符串型 OPC UA NodeId 的参数映射，数字型 NodeId 显式暂缓。
5. 将 TCP 改为批量发送，取消逐节点地址。
6. 增加跨客户端预检和事务化导入；客户端必须提前创建。

### P1

7. 为每条 OUTPUT 路由保存最新期望值和交付状态。
8. 目标重连后补发最新期望值。
9. 多目标发送按目标隔离，避免慢目标阻塞其他目标。
10. 增加路由级成功、失败、超时和重试可观测性。

### P2

11. 支持同一用户代码配置多个客户端连接。
12. 增加总表版本、导入批次和变更审计。
13. 使用真实总表做导入、重连、离线恢复和多目标分发压力测试。

## 8. 验收建议

一份总表导入至少应满足：

- 原始燃气总表无需人工改列即可预检；
- 200 个逻辑点、366 条输出关系全部有明确归一化结果；
- 所有目标测点都能解析到稳定 `PointId`；
- 字符串型 OPC UA 参数有确定映射，数字型 NodeId 被显式标记；
- `SWGZ` 作为只输出客户端能够导入；
- TCP 目标使用批量发送模型；
- 任一客户端保存失败时不会留下半套配置；
- 多个集成方在线时均能收到同一次 INPUT 变化；
- 集成方离线后恢复时能收到最新期望值或有明确的丢包策略；
- 管理界面能查看每条路由的交付状态和最后错误。

## 9. 当前内置样例

服务端空库首次启动时会创建“燃油系统”样例系统。样例直接使用内嵌的原始总表
`fuel-csv-utf8.csv`，并调用正式燃气总表导入服务：

```text
fuel-csv-utf8.csv
  → GasMasterTableService
  → 燃油系统
```

样例包含：

- 5 个预创建客户端：FZXT、SWGZ、SWSC、SWXT、XNCZ；
- 200 个 INPUT 端点；
- 192 个 OUTPUT 端点；
- 732 条统一 PointLink 声明：366 条输出关系、366 条输入来源关系；
- 每条路由保留 OPC UA 原始参数，并为可支持的字符串型 NodeId 生成 NodeId；
- 数字型 OPC UA NodeId 标记为暂不支持；
- TCP 路由不要求逐节点地址。

样例只负责建立系统、客户端和点表/路由数据，不创建客户端连接地址或凭据。
